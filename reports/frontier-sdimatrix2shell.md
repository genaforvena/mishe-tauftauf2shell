# frontier-sdimatrix2shell — imatrix loader duplicate-name OOB WRITE (CVE-2026-70659)

## Claim source and scope

- GitHub security advisory GHSA-6q7q-2v9c-x8m7 (published 2026-09-27):
  https://github.com/leejet/stable-diffusion.cpp/security/advisories/GHSA-6q7q-2v9c-x8m7
  — `IMatrixCollector::load_imatrix` (`src/runtime/imatrix.cpp`) resizes an
  entry's `values`/`counts` vectors only when they are empty; two entries with
  the same tensor name collapse in `std::unordered_map`, so a second, larger
  `nval` writes past both heap buffers. Affected
  `master-742-1a13107 -> master-763-4fcc6fe`; fixed in `master-763-4fcc6fe`.
  The advisory says value, int and OOB length are attacker-controlled.
- CVE-2026-70659 (CWE-787, CWE-1284, CVSS 3.1 7.8, Awaiting Analysis):
  https://cvefeed.io/vuln/detail/CVE-2026-70659. The advisory's "may be
  exploitable further" prose is a claim, not a local result.
- Fix commit `4fcc6fef10c6f686801c6e257b22cd6a3deb906b`
  (https://github.com/leejet/stable-diffusion.cpp/commit/4fcc6fef10c6f686801c6e257b22cd6a3deb906b):
  four lines in `src/runtime/imatrix.cpp` reject a repeated entry whose value
  count differs. Tag SHAs verified with `git ls-remote`:
  `master-742-1a13107 = 1a13107bac236…` (vulnerable),
  `master-763-4fcc6fe = 4fcc6fef10c6…` (fixed).

## Source-bound mechanism

In both pinned tags, verbatim `src/runtime/imatrix.cpp:253` defines
`IMatrixCollector::load_imatrix`. Each entry does
`auto& e = stats_[std::move(name)]` into an
`unordered_map<string, IMatrixStats>`; `IMatrixStats` owns
`vector<float> values` and `vector<int> counts`. Verbatim `:287-289` resizes
both vectors to `nval` **only if `e.values.empty()`**. A second entry with the
same name reuses that `IMatrixStats`, so `:301-303` runs
`e.values[i] += tmp[i]; e.counts[i] += ncall;` for the second `nval` against
the first entry's vector sizes. The fixed tag adds at verbatim `:290-294`:
`else if (e.values.size() != (size_t)nval) { LOG_ERROR(...); stats_ = {}; return false; }`.
The sibling `collect_imatrix` in the same file already performs the matching
size check, so this is a missing guard, not a documented format feature.

## Local experiment (rung 3 observed, rung 4 PARTIAL)

`lab/frontier/sdimatrix2shell/run-all.sh` verifies pinned tarball, fix-patch
and harness SHA-256s, extracts the verbatim `load_imatrix` body from line 253
to EOF of each tag (with `#line 253` so sanitizer traces name the real source
line), compiles it under GCC+Clang ASan and GCC+Clang plain, and drives a
crafted binary `.imatrix` generated by `mkinput.cpp`: two entries named
`blk.0`, first `nval=1`, second `nval=3`, with `ncall=0x41414141` and float
payload carrying chosen bits. No model file, CLI, listener, socket or external
target is used.

Observed with runner sha256
`aea439caffe5b9878d72c669da6577e17cdd62777b7dcae507797c4481bb77b9`:
**RESULT PASS=10 FAIL=0, rc 0**. On the vulnerable tag both compilers report
`ERROR: AddressSanitizer: heap-buffer-overflow`, `READ of size 4`, 0 bytes
after the 4-byte `values` region, at verbatim `src/runtime/imatrix.cpp:302`
in `IMatrixCollector::load_imatrix` — the `+=` reads the out-of-range element
before writing it. On the fixed tag the same file prints
`inconsistent size for a repeated entry (1 vs 3)` and `ok=0` with no ASan
report; safe distinct-name inputs succeed on both tags. In plain vulnerable
builds the chosen `ncall` int appears at `counts.data()[1]` and
`counts.data()[2]`, two ints past the 1-element `counts` vector, on both
compilers (`counts_oob1=0x41414141 counts_oob2=0x41414141`); the safe control
prints zeros there. Full pins, hashes and preserved negatives are in
`lab/frontier/sdimatrix2shell/PROVENANCE.md`.

Grade: **rung 3 verbatim / rung 4 PARTIAL**. ASan confirms a deterministic OOB
access from an input-controlled length at the pinned sink, and the plain build
puts attacker-chosen int bytes at chosen offsets past a named vector's logical
end. Those bytes stay inside that vector's malloc chunk: no named *adjacent*
object, pointer control, CLI/`--imat-in` path, live process, command execution
or r5. Advisory RCE framing remains a claim.

## Cheapest next rung-moving experiment

Build the pinned `sd-cli` and feed the exact crafted file through
`sd-cli -M convert --imat-in poc.imatrix -o out.gguf` (the advisory reports the
imatrix loads before a model is required), on local files only; compare
vulnerable crash / fixed rejection. To advance rung 4 beyond PARTIAL, measure a
placement where chosen bytes land in a named adjacent object without first
corrupting the `counts` chunk's metadata: the two arrays are indexed by the
same `i`, and with equal-sized chunks the `values` overflow reaches the next
object only at `i >= chunksize/4` while the `counts` overflow has already
passed its own usable area at `i >= chunksize/4 - 3`. Would also change the
assessment: a fixed-tag ASan report, a witness counterexample, or a live
CLI-path observation contradicting these labels.
