# asn1scc2shell — consumer-reality check (2026-11-21)

Status: **bounded rung-4 boundary reached; one negative and five positive results, all measured.** Loopback-only, 127.0.0.1, pinned bytes. Author report; Results 1–2 replayed by W74 #944, Result 3 by W78 #967, Results 4–5 by W74 #974 and #980 respectively — **all five results ESTABLISHED AS CLAIMED** at the labeled grades, no NIT. The witness's Result 4 control (wire bytes carrying `safe_handler` instead of `marker`) returned SAFE, consistent with the claim that the wire value, not packet length alone, selects the target. No further witness replay owed.

## Question

AGENTS.md requires the consumer's actual behavior on this host before exploitation mechanics. Frontier's rung-4 evidence used an artificial `malloc(9)` staging allocation for a generated `Payload` whose real `sizeof` is 12. Does the over-range uPER size-field write reach a live heap neighbour in a consumer that allocates the generated type naturally?

## Method

`lab/frontier/asn1scc2shell/consumer-service.c` (+ `consumer.sh`, `watch.gdb`),
`variant-service.c` (+ `variant.sh`, `watch-variant.gdb`), `heap-chain.c`
(+ `heap-chain.sh`, `watch-chain.gdb`), `pointer-target.c`
(+ `pointer-target.sh`, `watch-pointer.gdb`) and `pie-partial.c`
(+ `pie-partial.sh`): TCP services bound to 127.0.0.1
that accept one hostile packet and call the generated `Payload_Decode`
against the verbatim pinned 4.6.0.17 runtime (built by `run.sh` from pinned
tarballs, decoder generated by the pinned 4.7.0.1 compiler). The first service
offers two allocation modes: `natural` = `malloc(sizeof(Payload))`, `exact` =
`malloc(9)` (frontier staging). A separate client sends each packet on
loopback. Instrumented with ASan and gdb hardware watchpoints on the first byte
past the declared array, on the next malloc chunk's size field, on a live
neighbour Payload's fields after the corrupted chunk is consumed by malloc
and on a live callback pointer in a lab consumer struct; the PIE probe uses a
two-connection loopback service that leaks that pointer's low 16 bits first.
Logs and binaries: `lab/frontier/asn1scc2shell/run/` (gitignored).

## Result 1 — pinned schema `SIZE(0..5)`: NEGATIVE for neighbour reach

`sizeof(Payload) = 12` (`int nCount` at 0, `byte arr[5]` at 4, **3 bytes tail padding** at 9..11). The decoded count 7 writes arr[0..6], i.e. object offsets 4..10.

- ASan, pinned 4.6.0.17, `natural` allocation, hostile packet: **clean** — `ok=0 err=1 decoded=7`, object bytes `07 00 00 00 5a a5 5a a5 5a a5 5a 00`. The two past-array bytes at offsets 9/10 stay inside the object.
- ASan, same build, `exact` allocation: `WRITE of size 1`, 0 bytes after a 9-byte region, frames `asn1crt_encoding.c:400` ← `:1449` ← generated `schema.c:59`. This reproduces frontier's rung 3/4 through the real socket but only with the artificial 9-byte destination.
- gdb, plain glibc, `natural`: hardware watchpoint on `obj+9` fires inside `BitStream_ReadByteArray` at `asn1crt_encoding.c:401` (partial store 0xa0, OR-completed to 0xa5), called via `:1449` ← `schema.c:59` ← `service.c:114`. The malloc chunk's size field at `obj-8` is `0x21` (32-byte chunk, 24 usable bytes). Post-decode object `07 00 00 00 5a a5 5a a5 5a a5 5a 00`; offsets 11..23 zero; the **next chunk's size field at `obj+24` reads `0x20d51` both before and after** — untouched.

Conclusion: for the pinned schema and a natural allocation of its generated type, the 2-byte overflow is absorbed by struct tail padding. No memory corruption past the object, no neighbour header touched, no pointer or control-flow target reachable. Frontier's past-end bytes were real stores from the runtime but landed in staging; the natural allocation does not expose a neighbour through this path.

## Result 2 — schema variant `SIZE(0..17)`: POSITIVE, chosen bytes in live heap metadata

Same pinned runtime and compiler, only the schema changed. Generated `Payload` is `{ int nCount; byte arr[17]; }`, `sizeof = 24` with no effective slack for the decoded length: the 5-bit size field decodes 31, so 14 bytes land past `arr[16]`. A natural `malloc(sizeof(Payload))` of 24 bytes exactly fills a glibc 32-byte chunk's 24 usable bytes, so the overflow reaches the next chunk.

- ASan, pinned 4.6.0.17, natural 24-byte allocation, hostile packet count=31: `WRITE of size 1`, 0 bytes after a 24-byte region, frames `asn1crt_encoding.c:400` ← generated `schema.c:59`. Benign count=2 clean.
- gdb, plain glibc: hardware watchpoint on `obj+24` fires in the same runtime store loop. Pre-write next-chunk size field `0x20d51` (live top-chunk metadata); post-write `0xa55aa55aa55aa55a`, with the eight bytes at `obj+24..31` reading `5a a5 5a a5 5a a5 5a a5` — **two distinct attacker-chosen values, byte-exact, in a real neighbour's size field**, from a natural allocation, with no guard page or staging region.
- Fixed 4.7.0.1 control on the variant: clean, `decoded=0`, object all zeros. Its generated wrapper still returns `ok=1 err=0` (it overwrites the runtime error), so do not claim the wrapper rejects.

Conclusion: the padding absorption in Result 1 is schema-specific, not a property of the runtime bug. With a generated type whose array leaves no overflow slack, the same pinned vulnerable runtime writes chosen bytes into live malloc metadata through a normal generated decoder call.

## Result 3 — corrupted metadata consumed: overlapping allocation writes a live ASN1SCC field

`heap-chain.c` keeps the same pinned runtime, generated `SIZE(0..17)` decoder
and loopback socket, but allocates four consecutive 24-byte `Payload` objects
`A/B/C/D` (chunks at `A-16`, `A+16`, `A+48`, `A+80`). `B`'s size field is at
`A+24`, inside `A`'s overflow range. The hostile packet's byte 20 is chosen as
`0x41`; the runtime's per-byte store sets `B`'s size field from `0x21` to
`0x41` while leaving `C` and `D` intact.

- Vulnerable pinned 4.6.0.17, `count=31`, chosen bytes `00*20 41 00*10`:
  `decoded=31`, `ok=0 err=1`, `B size field at A+24: 0x21 -> 0x41`.
  `free(B)` routes by the claimed `0x40` size into that tcache bin; the next
  `malloc(56)` returns `ov=B` at `C-32` (usable 24 for `C`). Stores
  `ov[32]=0x77` and `ov[36]=0x42` change live `C->nCount` from `0x11223344`
  to `0x11223377` and `C->arr[0]` from `0x11` to `0x42`. Reads back:
  `ov[32..39] = 77 33 22 11 42 11 11 11`. The changed bytes are supplied by
  the test after the decode; they are not the decoder's own payload bytes.
- gdb hardware watchpoint on `C`'s first byte: old `0x44` -> new `0x77`, stop
  in `main` at `heap-chain.c:166`, i.e. the store came through the legitimate
  `malloc` result, not through `Payload_Decode`.
- Fixed 4.7.0.1 control, same packet: `B size field 0x21 -> 0x21`, `ov=C+64`
  from the top chunk (no overlap), `C->nCount=0x11223344`, `C->arr[0]=0x11`
  unchanged; wrapper still returns `ok=1 err=0 decoded=0` (error overwritten).
- Five identical runs had identical address-masked semantic output. The reported
  digest is an **ad-hoc** normalization (hex addresses replaced by placeholders);
  no committed normalizer reproduces that exact hash. W78 #967 independently
  verified the semantic determinism and flagged the missing recipe as a NIT.

Conclusion: chosen bytes in live heap metadata are consumable by the host's
real allocator. A normal `free`/`malloc` pair turns the corrupted size into an
overlapping chunk, and a store through that chunk changes fields of a live
generated ASN1SCC object. This is an arbitrary-write **window inside the
heap**, not a pointer, PC or control-flow write. It uses the same generated
decoder as Result 2, with ordinary allocator grooming, not a different schema
or a staging allocation.

## Result 4 — wire-chosen callback pointer: benign marker execution in a lab consumer

`pointer-target.c` (+ `pointer-target.sh`, `watch-pointer.gdb`) builds a
loopback service whose heap `Session` embeds the generated `SIZE(0..17)`
`Payload` as its first member and keeps a `void (* volatile handler)(void)`
at `Session+24` (`sizeof(Session)=40`). `Payload` occupies offsets 0..23, so
the array copy at generated `schema.c:59` reaches `Payload` offsets 24..34:
chosen bytes 20..27 land byte-exact on the pointer, bytes 28..30 on the
following canary. Both builds are `-no-pie` so the wire can carry the address
of a benign `marker()`; no other packet condition changed from Result 2.

- Vulnerable pinned 4.6.0.17, count=31, chosen
  `5a*20 d0 28 40 00 00 00 00 00 cc cc cc` (little-endian
  `marker=0x4028d0`): `ok=0 err=1 decoded=31`, `handler=0x4028d0` with bytes
  `d0 28 40 00 00 00 00 00`, canary `cc cc cc c0 c0 c0 c0 c0`. The following
  `s->handler()` printed `MARKER: control-flow diverted to chosen address`
  and exited rc 0. The ASan build emitted no diagnostic: the overflow crossed
  from the generated subobject into the enclosing `Session`, not a heap
  redzone.
- gdb hardware watch on the live `s->handler`: old `0x4015b6 <safe_handler>`
  -> new `0x4015c0`, stopping in `BitStream_ReadByteArray` at
  `asn1crt_encoding.c:401` <- `BitStream_DecodeOctetString_no_length:1449` <-
  generated `schema.c:59` <- `main` — the same pinned runtime store as
  Results 1–3, not an injected write.
- Fixed 4.7.0.1 control, same layout and packet shape with its own marker
  address: `handler=0x402936=safe_handler`, canary all `c0`,
  `SAFE: original handler intact`, wrapper `ok=1 err=0 decoded=0`.
- Witness W74 #974 replayed this result from clean archive `2de7032` and
  **ESTABLISHED AS CLAIMED** at this grade: `handler=0x4028d0=marker`, bytes
  `d0 28 40 00 00 00 00 00`, canary `cc cc cc c0 c0 c0 c0 c0`, `MARKER`
  printed rc0; fixed `handler=0x402936=safe`, canary `c0*8`, `SAFE`; gdb
  hardware watch old `0x4015b6` -> new `0x4015c0` at
  `asn1crt_encoding.c:401` <- `:1449` <- `schema.c:59`. Its control — the same
  vulnerable binary with wire bytes 20..27 set to `safe_handler=0x4028b6` —
  produced `handler=b6 28 40 00 00 00 00 00`, intact canary and `SAFE`, i.e.
  the decoded wire value, not the packet length alone, selects the target.

Conclusion: with a consumer layout that places a callback immediately after
the generated decoded object, the vulnerable runtime's own wire bytes overwrite
a live function pointer and a call through it reaches the chosen benign marker.
The layout, non-PIE address and marker are lab conditions, NOT an observed
real ASN.1 application; no shellcode, no real target, no arbitrary-address
primitive.

## Result 5 — PIE/ASLR partial-pointer overwrite with a 16-bit leak

`pie-partial.c` (+ `pie-partial.sh`) removes Result 4's hardcoded `-no-pie`
address. The same heap `Session` and pinned `SIZE(0..17)` decoder are rebuilt
`-fPIE -pie` (`/proc/sys/kernel/randomize_va_space = 2`). The hostile decoded
count is **22**, not 31: chosen bytes 0..19 fill the array and its slack, and
only chosen bytes 20..21 reach `Session+24..25`, the low two bytes of the live
handler pointer. Bytes 26..31 of that pointer and the canary at 32..39 are
never written. The service takes two loopback connections: the first returns a
diagnostic-shaped `LEAK %04x` line containing the low 16 bits of its live
handler, and the second receives the hostile packet. The client adds the
binary's compile-time `marker - safe_handler` offset (`nm` reports delta
`0x1a` = 26) to the leaked low 16 bits; no full code address is on the wire.

- Five vulnerable pinned 4.6.0.17 runs produced five distinct PIE bases
  (`orig_handler` `0x5e92ed29f629`, `0x5a6611cd9629`, `0x5f95cfe05629`,
  `0x593cd4c99629`, `0x618c77cca629`). In each, `decoded=22`, `ok=0 err=1`,
  the handler became the run's `marker` address (`0x…f629` -> `0x…f643`),
  `high6_same=1`, the canary stayed `c0 c0 c0 c0 c0 c0 c0 c0`, and the call
  printed `MARKER: control-flow diverted to chosen address`. One example's
  pointer bytes went `29 f6 29 ed 92 5e 00 00` -> `43 f6 29 ed 92 5e 00 00`:
  only byte 0 changed, because the 26-byte offset did not carry into byte 1.
- Fixed 4.7.0.1 control with the same packet shape and its own delta:
  `ok=1 err=0 decoded=0`, handler `0x…9669` unchanged and equal to
  `safe_handler`, canary intact, `SAFE: original handler intact`. The wrapper
  caveat from Results 2–4 still applies.
- Counterfactual with the identical count-22 store but `delta=0`, so the two
  wire bytes reproduce the live low 16 bits: `ok=0 err=1 decoded=22`, handler
  unchanged, `SAFE: original handler intact`. The chosen two bytes, not the
  packet length alone, cause the diversion.
- A PIE ASan build of the pinned vulnerable runtime reached the marker with no
  `ERROR: AddressSanitizer` diagnostic — the store crosses a generated
  subobject boundary inside `Session`, not a redzone, as in Result 4.
- Witness W74 #980 replayed this result from clean archive `b8b20c6` and
  **ESTABLISHED AS CLAIMED** at this grade: `/proc/sys/kernel/randomize_va_space=2`,
  `nm` delta marker-safe_handler `0x1a` (26) confirmed, five distinct PIE bases,
  count=22, handler low16 advanced by 26 with `high6_same=1`, intact canary,
  `MARKER` in all five; fixed 4.7.0.1 safe; `delta=0` counterfactual safe; ASan
  PIE no redzone diagnostic. No NIT.

Conclusion: under PIE and host ASLR, a 16-bit pointer leak plus the pinned
decoder's two-byte overrange write is enough to divert a live callback to a
chosen nearby function; the upper 48 bits come from the untouched live
pointer, not from the wire. Boundary: a lab-constructed consumer, a
diagnostic-shaped leak, a fixed intra-binary offset and a benign marker — no
real ASN.1 application, no full-address write, no shellcode and no RCE.

## Rung grading and boundaries

- Rungs 1/2/3: ESTABLISHED (frontier, re-verified wake 1, 12 PASS / 0 FAIL).
- Rung 4: **instrumented chosen bytes in harness staging** (frontier) **and, for the SIZE(0..17) variant, chosen bytes at chosen offsets in live malloc chunk metadata from a natural allocation, then in a neighbouring live ASN1SCC object's fields through an overlapping malloc result** (Results 2–3). Result 4 adds **wire-chosen function-pointer overwrite and benign marker execution in a lab-constructed consumer layout**; Result 5 shows the same diversion under **PIE and host ASLR with only two wire bytes and a 16-bit pointer leak**. The store path is the real pinned runtime, not a shim.
- Still UNKNOWN: any real ASN.1-speaking application or listener, a leak in such an application, a full arbitrary-address write and code other than the benign marker. Pointer control and benign marker execution are LAB DEMONSTRATED under the constructed `Session` layout (Result 4 non-PIE, Result 5 PIE/ASLR with a diagnostic-shaped 16-bit leak), not observed in a real consumer. The overlapping chunk in Result 3 remains a heap-internal write window. The variant is a generated schema different from the pinned harness's `SIZE(0..5)` type — it demonstrates the general primitive's condition, not that the pinned type alone reaches a neighbour. No probe left loopback.
