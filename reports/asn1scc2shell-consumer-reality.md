# asn1scc2shell — consumer-reality check (2026-11-21)

Status: **bounded rung-4 boundary reached; one negative and two positive results, all measured.** Loopback-only, 127.0.0.1, pinned bytes. Author report; Results 1–2 replayed by W74 #944 ESTABLISHED AS CLAIMED, Result 3 replay requested.

## Question

AGENTS.md requires the consumer's actual behavior on this host before exploitation mechanics. Frontier's rung-4 evidence used an artificial `malloc(9)` staging allocation for a generated `Payload` whose real `sizeof` is 12. Does the over-range uPER size-field write reach a live heap neighbour in a consumer that allocates the generated type naturally?

## Method

`lab/frontier/asn1scc2shell/consumer-service.c` (+ `consumer.sh`, `watch.gdb`),
`variant-service.c` (+ `variant.sh`, `watch-variant.gdb`), and `heap-chain.c`
(+ `heap-chain.sh`, `watch-chain.gdb`): TCP services bound to 127.0.0.1 that
accept one hostile packet and call the generated `Payload_Decode`
against the verbatim pinned 4.6.0.17 runtime (built by `run.sh` from pinned
tarballs, decoder generated by the pinned 4.7.0.1 compiler). The first service
offers two allocation modes: `natural` = `malloc(sizeof(Payload))`, `exact` =
`malloc(9)` (frontier staging). A separate client sends each packet on
loopback. Instrumented with ASan and gdb hardware watchpoints on the first byte
past the declared array, on the next malloc chunk's size field, and on a live
neighbour Payload's fields after the corrupted chunk is consumed by malloc.
Logs and binaries: `lab/frontier/asn1scc2shell/run/` (gitignored).

Reproduce from `lab/frontier/asn1scc2shell/`:
```
bash run.sh run && bash consumer.sh && bash variant.sh && bash heap-chain.sh

# pinned-schema gdb watchpoint:
```

## Result 1 — pinned schema `SIZE(0..5)`: NEGATIVE for neighbour reach

`sizeof(Payload) = 12` (`int nCount` at 0, `byte arr[5]` at 4, **3 bytes tail padding** at 9..11). The decoded count 7 writes arr[0..6], i.e. object offsets 4..10.

- ASan, pinned 4.6.0.17, `natural` allocation, hostile packet: **clean** — `ok=0 err=1 decoded=7`, object bytes `07 00 00 00 5a a5 5a a5 5a a5 5a 00`. The two past-array bytes at offsets 9/10 stay inside the object.
- ASan, same build, `exact` allocation: `WRITE of size 1`, 0 bytes after a 9-byte region, frames `asn1crt_encoding.c:400` ← `:1449` ← generated `schema.c:59`. This reproduces frontier's rung 3/4 through the real socket but only with the artificial 9-byte destination.
- gdb, plain glibc, `natural`: hardware watchpoint on `obj+9` fires inside `BitStream_ReadByteArray` at `asn1crt_encoding.c:401` (partial store 0xa0, OR-completed to 0xa5), called via `:1449` ← `schema.c:59` ← `service.c:114`. The malloc chunk's size field at `obj-8` is `0x21` (32-byte chunk, 24 usable bytes). Post-decode object `07 00 00 00 5a a5 5a a5 5a a5 5a 00`; offsets 11..23 zero; the **next chunk's size field at `obj+24` reads `0x20d51` both before and after** — untouched.

Conclusion: for the pinned schema and a natural allocation of its generated type, the 2-byte overflow is absorbed by struct tail padding. No memory corruption past the object, no neighbour header touched, no pointer or control-flow target reachable. Frontier's past-end bytes were real stores from the runtime but landed in staging; the natural allocation does not expose a neighbour through this path.

## Result 2 — schema variant `SIZE(0..17)`: POSITIVE, chosen bytes in live heap metadata

Same pinned runtime and compiler, only the schema changed. Generated `Payload` is `{ int nCount; byte arr[17]; }`, `sizeof = 24` with no effective slack for the decoded length: the 5-bit size field decodes 31, so 14 bytes land past `arr[16]`. A natural `malloc(sizeof(Payload))` of 24 bytes exactly fills a glibc 32-byte chunk's 24 usable bytes, so the overflow reaches the next chunk.

- ASan, pinned 4.6.0.17, natural 24-byte allocation, hostile packet count=31: `WRITE of size 1`, 0 bytes after a 24-byte region, frames `asn1crt_encoding.c:400` ← generated `schema.c:59`. Benign count=2 clean.
- gdb, plain glibc: hardware watchpoint on `obj+24` fires in the same runtime store loop. Pre-write next-chunk size field `0x20d51` (live top-chunk metadata); post-write `0xa55aa55aa55aa55a`, with the eight bytes at `obj+24..31` reading `5a a5 5a a5 5a a5 5a a5` — **two distinct attacker-chosen values, byte-exact, in a real neighbour's size field**, from a natural allocation, with no guard page or staging region.
- Fixed 4.7.0.1 control on the variant: clean, `decoded=0`, object all zeros. Its generated wrapper still returns `ok=1 err=0` (it overwrites the runtime error), so do not claim the wrapper rejects.

Conclusion: the padding absorption in Result 1 is schema-specific, not a property of the runtime bug. With a generated type whose array leaves no overflow slack, the same pinned vulnerable runtime writes chosen bytes into live malloc metadata through a normal generated decoder call.

## Result 3 — corrupted metadata consumed: overlapping allocation writes a live ASN1SCC field

`heap-chain.c` keeps the same pinned runtime, generated `SIZE(0..17)` decoder
and loopback socket, but allocates four consecutive 24-byte `Payload` objects
`A/B/C/D` (chunks at `A-16`, `A+16`, `A+48`, `A+80`). `B`'s size field is at
`A+24`, inside `A`'s overflow range. The hostile packet's byte 20 is chosen as
`0x41`; the runtime's per-byte store sets `B`'s size field from `0x21` to
`0x41` while leaving `C` and `D` intact.

- Vulnerable pinned 4.6.0.17, `count=31`, chosen bytes `00*20 41 00*10`:
  `decoded=31`, `ok=0 err=1`, `B size field at A+24: 0x21 -> 0x41`.
  `free(B)` routes by the claimed `0x40` size into that tcache bin; the next
  `malloc(56)` returns `ov=B` at `C-32` (usable 24 for `C`). Stores
  `ov[32]=0x77` and `ov[36]=0x42` change live `C->nCount` from `0x11223344`
  to `0x11223377` and `C->arr[0]` from `0x11` to `0x42`. Reads back:
  `ov[32..39] = 77 33 22 11 42 11 11 11`. The changed bytes are supplied by
  the test after the decode; they are not the decoder's own payload bytes.
- gdb hardware watchpoint on `C`'s first byte: old `0x44` -> new `0x77`, stop
  in `main` at `heap-chain.c:166`, i.e. the store came through the legitimate
  `malloc` result, not through `Payload_Decode`.
- Fixed 4.7.0.1 control, same packet: `B size field 0x21 -> 0x21`, `ov=C+64`
  from the top chunk (no overlap), `C->nCount=0x11223344`, `C->arr[0]=0x11`
  unchanged; wrapper still returns `ok=1 err=0 decoded=0` (error overwritten).
- Five identical runs have identical semantic digests
  `sha256=bf07a5b48a80b23b6fab5ec6a2c5495324c214505f2251a2e6b58782c796c7d0`
  (addresses masked).

Conclusion: chosen bytes in live heap metadata are consumable by the host's
real allocator. A normal `free`/`malloc` pair turns the corrupted size into an
overlapping chunk, and a store through that chunk changes fields of a live
generated ASN1SCC object. This is an arbitrary-write **window inside the
heap**, not a pointer, PC or control-flow write. It uses the same generated
decoder as Result 2, with ordinary allocator grooming, not a different schema
or a staging allocation.

## Rung grading and boundaries

- Rungs 1/2/3: ESTABLISHED (frontier, re-verified wake 1, 12 PASS / 0 FAIL).
- Rung 4: **instrumented chosen bytes in harness staging** (frontier) **and, for the SIZE(0..17) variant, chosen bytes at chosen offsets in live malloc chunk metadata from a natural allocation and then in a neighbouring live ASN1SCC object's fields through an overlapping malloc result** (Results 2–3). The store path is the real pinned runtime, not a shim.
- Still UNKNOWN: any real ASN.1-speaking application or listener, pointer control, control-flow diversion, benign marker execution, or full arbitrary-address write. The overlapping chunk gives a write window inside the heap, not a pointer or PC. The variant is a generated schema different from the pinned harness's `SIZE(0..5)` type — it demonstrates the general primitive's condition, not that the pinned type alone reaches a neighbour. No probe left loopback.
