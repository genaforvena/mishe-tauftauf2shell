# frontier-soxng2shell — VOC ADPCM cross-block heap OOB WRITE (CVE-2026-129264)

Status: **STAGED, rung 3 ASan-confirmed in verbatim pinned source through the
shipped `sox_ng` CLI (W281, 2026-11-26)**. A deterministic 8,494-byte `.voc`
file first fills the 8,192-sample effect buffer with 8-bit blocks, then switches
to a 4-bit ADPCM block without recomputing `per`; the loop reserves one output
sample per iteration but writes two. Pins, hashes, refetch URLs and preserved
negatives are in `lab/frontier/soxng2shell/PROVENANCE.md`.

## Claim source and scope

- CVE record (CNA VulDB): `https://cve.org/CVERecord?id=CVE-2026-129264`,
  published 2026-11-14, title "sox_ng VOC Decoder voc.c read_samples_voc
  out-of-bounds write", CWE-119 + CWE-787, affected 14.8.0 and 14.8.1. Claim:
  "Such manipulation leads to out-of-bounds write. The attack can be executed
  remotely. The exploit has been disclosed publicly and may be used."
- NVD mirror: `https://nvd.nist.gov/vuln/detail/CVE-2026-129264` (Deferred).
  GitHub Advisory Database: GHSA-gwh5-2vhj-gvcc, unreviewed/low, affected and
  patched versions UNKNOWN; not used as the version authority.
- Upstream issue 873: `https://codeberg.org/sox_ng/sox_ng/issues/873`. Reporter:
  "`read_samples_voc()` computes the per-iteration sample count per once, before
  its main loop, and never recomputes it. If `v->size` changes mid-loop, the
  loop body writes more samples per iteration than the guard reserved"; "The
  data comes from the input file, so the attacker has partial control over what
  is written out of bounds." Maintainer confirms the fix in main and 14.[78].X
  and downplays exploitability.
- Fix commit `0b40408b516a3628cfcfd83d32028cf361c8ac90` (2026-10-03, parent
  `3f57d64126d6839855452310cfc5c3b267c17955`, one file `src/voc.c`, +41/-20),
  first fixed release tag `sox_ng-14.9.0`
  (`6edd3b3ae204908101a8c1bd54903971e0393b4d`, 2026-11-18). Vulnerable pin:
  tag `sox_ng-14.8.1` (`a4a14b4f58ac2c08c4cc416a7cffe8a4c50a0b7d`). The
  local fixed control is the vulnerable tag plus the single fix patch, so the
  before/after difference is attributable to that patch alone.

## Source-bound mechanism

`read_samples_voc()` computes `size_t per = max(1, 9 / v->size)` once before the
loop and guards with `done + per <= len`. `getblock()` reassigns `v->size` from
the next VOC_DATA_16 block's `bBitsPerSample` with no cross-block consistency
check. Switching from an 8-bit block (`per == 1`) to a 4-bit CRLADPCM4 block
makes the body execute two `*buf++ = SOX_SIGNED_16BIT_TO_SAMPLE(...)` stores
(voc.c:413/415) per reserved iteration, so `buf` eventually crosses the end of
`sox_flow_effects()`'s `lsx_realloc_array(effp->obuf, len)` allocation. Fix:
recompute `per` after `getblock()` and `if (per > len - done) break;`.

## Local reproduction (observed, not inferred)

Built both sides from the pinned 14.8.1 tarball with autoreconf plus the
published dependency-free configure options and GCC ASan flags. The ordinary
`src/sox_ng` CLI, with no special options, decoded the generated PoC:

- Vulnerable: `AddressSanitizer: heap-buffer-overflow`, `WRITE of size 4` at
  verbatim `src/voc.c:415`, callers `sox_read` (`formats.c:1414`),
  `sox_read_wide` (`sox_ng.c:520`), `sox_flow_effects` (`effects.c:444`);
  address 0 bytes after a 32,768-byte region. Exit 1.
- Fixed (same source plus the one patch): exit 0, no ASan report.
- Safe 8-bit-only control: exit 0, no ASan report on both builds.

`run-all.sh` re-provisions the pinned bytes, rebuilds both CLIs, regenerates
the two `.voc` files and asserts all of the above. Raw logs and hashes are in
PROVENANCE. The public PoC generator and published ASan log are saved under
`lab/frontier/soxng2shell/src/`; the generated local PoC is 8,494 bytes (the
upstream prose says about 8.3 KB), and the local regenerated bytes are the
authority for these runs.

## Feasibility assessment

Tractability is high for a file-format write primitive: tiny deterministic
input, default shipped CLI, one-file fix, clean fixed/safe controls. Rung 4 is
NOT CLAIMED: the stored value is an ADPCM-derived `sox_sample_t`, only partly
influenced by the file; no chosen-offset readback, pointer overwrite,
control-flow steering, benign command, socket or daemon consumer was observed.
The CVE's "attack can be executed remotely" presupposes a victim decoding an
attacker-supplied file, not a listener in this lab. No plain-build crash was
reproduced locally; the minimal PoC's overflow is ASan-visible only (negative
preserved). Value control, readback and any shell path stay UNKNOWN.

Cheapest rung-moving experiment: on a plain (non-ASan) vulnerable build, vary
the 4-bit block fill bytes and length, use a heap-grooming prelude (other VOC
blocks or file-format conversions in the same process) to place a chosen
same-size object just past the 32,768-byte effect buffer, then observe decoded
output or a consumer readback at a chosen offset. Stop at a measured chosen
word; do not infer RCE from the advisory.
