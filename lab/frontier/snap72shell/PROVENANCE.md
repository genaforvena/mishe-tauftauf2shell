## Fixed control (not upstream)

`a4127166e9274f8fbefbda4f0536ad33808bed7135277ad93593ce02c322b233`. Derived
from the pinned vulnerable function by inserting the guard proposed in issue
#32 immediately before line 418:

- `MaxRecv = IsoSize - (ResHeaderSize23 + sizeof(TResFunReadParams)) - Offset - 4`
- `MaxDest = Item->Amount * DataSizeByte(Item->WordLen)`
- reject with `errCliInvalidPlcAnswer` and `break` when `Slice` exceeds either.

merged upstream. It is used only as the fixed control; the rung evidence comes
from the byte-exact vulnerable slice.

## Negative results preserved

- W136 screened Snap7 out for lack of patch bytes; the reopen rests on issue
  #32's proposed guard, not on a new upstream release.
- Only 32 real bytes are present in the crafted response. Beyond that offset
  the copied source is the zeroed PDU buffer, so `DEST64=00`; chosen-byte
  control is demonstrated at offsets 0 and 17, not past the real payload.
- At frontier staging, no fake PLC, socket or live snap7 client was exercised;
  the `isoExchangeBuffer()` stub injected the response locally. The W1 live
  wire experiment below supersedes that limitation; the scoped harness result
  is retained as the earlier, independent observation.
- An early 8192-byte plain-mode arena aborted with `double free or corruption`
  because the 65535-byte write crossed the allocation; the arena was enlarged
  to 200000 bytes so the scoped byte-observation mode stays in bounds. The ASan
  rung uses a separate one-byte allocation and is unaffected.

`fake_s7_server.py` binds only 127.0.0.1 on an ephemeral port, completes COTP
CR/CC and S7 Setup Communication (negotiated PDU 480), then answers one
`Cli_ReadMultiVars()` request from the real pinned client. The ASan client is
compiled from `s7_micro_client.cpp`, `s7_peer.cpp`, `s7_isotcp.cpp`,
`s7_text.cpp`, `snap_msgsock.cpp`, `snap_sysutils.cpp` and `snap_threads.cpp`
with gcc 13.3.0, `-std=gnu++11 -g -O0 -fsanitize=address`. No external host is
contacted; no real PLC is involved.

Observed in two consecutive `run_live.sh` replays, normalized trace SHA-256
`1f25bf6311e1a659e4da947abc07d001cfacc5fe39dd67618560e425df3773d4`
(`live/evidence/normalized.txt`, `replay1.txt`, `replay2.txt`):

- Vulnerable, attack response: `DECLARED_DATA_LENGTH=65535 REAL_BYTES=32`;
  the server sent `...0401ff09ffff5a6b5a6b...` after a valid COTP CC and S7
  negotiate. The live client connected (`CLIENT_CONNECT_RC=0`) and ASan
  reported `heap-buffer-overflow`, `WRITE of size 65535`, 0 bytes after the
  one-byte caller allocation, frame
  `TSnap7MicroClient::opReadMultiVars()` at pinned line 418 via
  `PerformOperation()` and `ReadMultiVars()`; `client_rc=1`.
- Guarded build on the same attack wire: `CLIENT_READ_RC=8388608`,
  `ITEM_RESULT=8388608` (`errCliInvalidPlcAnswer`), `DST0=00`, ASan-clean;
  `client_rc=0`. This uses the issue-#32 derived control, not an upstream fix.
- Safe response (declared length 1, one real byte): vulnerable and guarded
  builds both returned `CLIENT_READ_RC=0`, `DST0=5a`, ASan-clean.
- Plain vulnerable build with a 200000-byte caller allocation, attack wire:
  `CLIENT_READ_RC=0 DST0=5a DEST17=6b DEST64=00`. The chosen wire bytes land
  at offsets 0 and 17 in a live client destination. Past the 32 real bytes
  the copied source is the zeroed PDU buffer, so `DEST64=00`; chosen-byte
  control is measured only inside the 32 real bytes.

Ceiling after W1: rung 4 **wire-reachable in the lab**, not scoped-only. The
65535-byte write is driven by a plant-started 127.0.0.1 responder into a live
pinned client process, and two chosen bytes land byte-exact. Attacker position
still requires PLC control or impersonation (`AT:P`); no upstream fixed
release exists; the guard is the reporter's proposal. No pointer redirect,
function-pointer overwrite, command execution or rung 5 observation. Raw
frames, ASan reports and server transcripts are in `live/evidence/`.
