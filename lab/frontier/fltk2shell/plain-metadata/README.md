# Plain-build glibc metadata observation (CVE-2026-135433)

Author-measured extension, wakes 3–4 (2026-11-24 ~06:21Z and ~06:42Z).
Unwitnessed; it does not change W195's ESTABLISHED rungs 1–4 verdict and is
**not** a rung-5 claim.

Question: with ASan removed, does the file-derived overwrite at `array-4..-1`
land in real allocator metadata? Answer: yes — it overwrites the high four
bytes of the glibc mmap chunk `size` field. It does not produce an observable
`free()` failure in this build: `munmap_chunk()` is reached with the corrupted
size and exits silently. No pointer/IP control, no command execution.

## Inputs

* `full-chosen.bmp` — copy of the established 118-byte `poc-chosen.bmp`
  (sha256 `135edc0a…3008`), same geometry `w=2 h=715827883 depth=24`.
* `short-chosen.bmp` — 60-byte variant generated by `gen_short.py` from the
  same header with only one 6-byte pixel row (`MISHE-`), sha256
  `2d26f388…8bf14`. Truncation stops the row loop after the first row so the
  destructor and `free()` are reached. No new geometry or new mechanism.
* `inputs.sha256` records all three fixtures.

## Measured

Vulnerable tree `fltk-1.4.5-plus1632` (only #1632's two edits applied to
release-1.4.5), built without sanitizers; driver is the unmodified
`../driver.cxx`, `g++ -g -O0`. Fixed control is `fltk-1.4.5-plus1647`
(`a28e392` casts) built the same way. Sources pinned by sha256 in
`build-info.txt`.

| case | vulnerable plain rc | fixed plain rc | observation |
|---|---|---|---|
| `full-chosen.bmp` | 139 | 0 | vulnerable: SIGSEGV at `Fl_BMP_Image.cxx:490` on row `y=715827879`, `ptr=array-22`, page before the mmap region; fixed: `fail=-3`, no crash |
| `short-chosen.bmp` | 0 | 0 | vulnerable: chunk `size` corrupted, `free()` reached, no diagnostic, no crash; fixed: `fail=-3`, no ASan/ abort |

gdb inspection of the vulnerable plain build:

* Before the first pixel write, at `Fl_BMP_Image.cxx:490`:
  `array = 0x7ffef75ff010`, `chunk.prev_size = 0`,
  `chunk.size = 0x0000000100001002` (4 GiB request + headers, page-rounded,
  `IS_MMAPPED`), from `x/2gx array-16`.
* After the first row, at `:510` (`short-chosen.bmp`):
  `chunk.size = 0x2d4d495300001002` — the high four bytes are the file's
  `53 49 4d 2d` ("SIM-"), i.e. attacker-chosen file bytes in an 8-byte glibc
  metadata word.
* Continuing that process: `munmap_chunk(p=0x7ffef75ff000)` is called from
  `__GI___libc_free(mem=array)` ← `Fl_RGB_Image::~Fl_RGB_Image` at
  `src/Fl_Image.cxx:460` ← `Fl_BMP_Image::~Fl_BMP_Image` ← `main` at
  `driver.cxx:12`. Process exits 0; no glibc diagnostic observed.

Raw transcripts: `outputs/gdb-header.txt`, `outputs/gdb-short.txt`,
`outputs/gdb-crash.txt`, `outputs/plain-*.out`. Exact commands in
`commands.txt`, exit codes in `exit-codes.txt`.

## Wake 4: both mmap chunk words are file-controlled (unwitnessed)

Wake 4 asks whether the negative row pointer can reach the whole 16-byte
glibc mmap header, not just the high half of `size`. New fixture
`prevsize.bmp` (77 bytes, sha256 `faef54c9…06c`, generated by
`gen_prevsize.py` from the pinned `poc-chosen.bmp`) uses
`w=8, h=0x0aaaaaaab, depth=24`. Then `start_y = h-1 = 178956970` and
`y*w*bDepth` wraps to −16, so the first row starts exactly at `array-16`,
the chunk header. The pixel bytes encode `prev_size = 0x3000` and
`size = 0x0000000200001002` (IS_MMAPPED bit and page-aligned low bits kept);
the 23rd pixel byte is withheld so the row loop stops at EOF before the
second row's wild write.

Measured in the same no-ASan trees:

* gdb at `Fl_BMP_Image.cxx:489`: `y=178956970`, `array=0x7ffef75ff010`,
  `ptr=array-16`, header `0x0 / 0x0000000100001002`.
* gdb at `Fl_Image.cxx:460` (destructor `delete[] array`): header
  `prev_size=0x0000000000003000`, `size=0x0000000200001002` — both exact
  file-derived words.
* gdb at `__GI_munmap`: `rdi=0x7ffef75fc000` (`chunk p − 0x3000`),
  `rsi=0x200004000` (`prev_size + masked size`); stack
  `__GI___libc_free(mem=array)` ← `Fl_RGB_Image::~Fl_RGB_Image` ←
  `Fl_BMP_Image::~Fl_BMP_Image` ← `main`.
* Exit codes: vulnerable plain `rc=139`, fixed plain `rc=0`. The same
  crafted file under gdb (ASLR disabled here) exits 0; the differing free
  outcome across runs is recorded, not explained. No chosen target address
  independent of the randomized mapping is claimed.

Raw: `outputs/gdb-prevsize.txt`, `outputs/plain-prevsize-vuln.out`,
`outputs/plain-prevsize-fixed.out`.

Preserved negative: the first attempt used `w=8, h=0x20000000` so the row
started at `array-24`. Bytes `array-24..-17` are the page **before** the
mmap region and unmapped; the process died at `:490` on the first write
(`ptr=array-24`, SIGSEGV) before reaching the destructor. Only offsets
`array-16..-1` (the header itself) are reachable in this mmap case; there is
no evidence for arbitrary bytes before the header.

## What was not measured

No chosen target address independent of the randomized mapping, no controlled
reuse after the crafted unmap, no heap layout groom beyond this mmap case, no
heap-chunk case for the pristine allocation-wrap geometry, no GUI/draw path,
no network surface, no pointer or IP control, no command execution, no rung 5.
The wake-3 silent `munmap_chunk()` is a negative result for turning that
particular metadata overwrite into an observable allocator failure; wake 4
changes the arguments, not the class of primitive.

## Reproduce

From `lab/frontier/fltk2shell/` (`driver-plain` is built by the established
`./run-all.sh`; all build products are local and uncommitted):

```
python3 plain-metadata/gen_short.py poc-chosen.bmp plain-metadata/short-chosen.bmp
# fixed plain tree, only if absent:
cmake -S fltk-1.4.5-plus1647 -B fltk-1.4.5-plus1647/build-plain \
  -DCMAKE_BUILD_TYPE=Debug -DFLTK_BUILD_TEST=OFF -DFLTK_BUILD_EXAMPLES=OFF \
  -DFLTK_BUILD_FLUID=OFF \
  -DOPTION_USE_SYSTEM_LIBJPEG=OFF \
  -DOPTION_USE_SYSTEM_LIBPNG=OFF -DOPTION_USE_SYSTEM_ZLIB=OFF \
  -DCMAKE_CXX_FLAGS='' -DCMAKE_EXE_LINKER_FLAGS=''
cmake --build fltk-1.4.5-plus1647/build-plain -j4 --target fltk fltk_images
g++ -g -O0 -o driver-plain-fixed driver.cxx \
  $(fltk-1.4.5-plus1647/build-plain/fltk-config --cxxflags --ldflags --use-images)
cd plain-metadata
for f in short-chosen full-chosen; do ../driver-plain "$f.bmp"; ../driver-plain-fixed "$f.bmp"; done
python3 ../gen_prevsize.py ../poc-chosen.bmp prevsize.bmp
../driver-plain prevsize.bmp; ../driver-plain-fixed prevsize.bmp
```
