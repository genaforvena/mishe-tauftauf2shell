# cjose2shell — provenance and harness notes (W180/W181, 2026-11-23)

## Claim and provisioning (read-only public sources)

- Advisory: `https://github.com/OpenIDC/cjose/security/advisories/GHSA-75r7-f5cv-g3wj`
  — "Heap buffer overflow in AES Key Wrap decryption (A128KW/A192KW/A256KW)",
  HIGH CVSS 8.2 `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:L/A:H`, CWE-122/CWE-787,
  CVE-2026-53938, published 2026-06-02. Affected `<= 0.6.2.4`, patched
  `>= 0.6.2.5`. The advisory's RCE language is a claim, not reproduced here.
- Fix commit `8c51d245273583a658f24ef7b08ba22f848a34a5` (parent
  `d2825697c4ce9edec1ee5f08509bba6a2df20e28`, 2026-06-02T09:22:36Z),
  patch URL `https://github.com/OpenIDC/cjose/commit/8c51d245.patch`.
- Source tarballs fetched from GitHub release-tag archives:
  `cjose-v0.6.2.4.tar.gz` (vulnerable), `cjose-v0.6.2.5.tar.gz` (upstream
  patched release, kept for cross-check only), `jansson-2.14.tar.gz`.
- All byte-exact pin hashes are in `PINS.sha256`, checked by `harness/run.sh`
  before every build. Vulnerable `src/vulnerable/src/jwe.c` SHA-256
  `a6945f0a7003...e387e6`; the fixed tree is the same v0.6.2.4 tarball with
  **only** the `src/jwe.c` hunk of `8c51d245` applied (SHA-256
  `9b45915478ad...70b`). CHANGELOG/test hunks of that commit were rejected
  by `patch` against the tag and were deliberately not backported; the
  security-relevant hunk applied with a -9 line offset and is the sole diff
  between the two trees.

## Build

Toolchain: gcc 13.3.0, clang 18.1.3, OpenSSL 3.0.13, locally built jansson
2.14 static library under `deps/jansson-prefix` (system has runtime
`libjansson.so.4` but no headers). No system package was installed.

- `deps/jansson-build/b`: cmake configure + build + install of jansson 2.14.
- `src/vulnerable`, `src/clang-vulnerable`: in-tree autotools builds of
  v0.6.2.4 with gcc / clang and `-fsanitize=address`.
- `src/fixed`, `src/clang-fixed`: same, with the single fix hunk applied.
- `src/plain-<cc>-<tree>`: four non-sanitized library builds so `plain`
  binaries link an unsanitized library (linking a sanitized library into a
  plain binary fails on ASan runtime symbols; this was observed and fixed by
  building separate plain libraries).
- `harness/run.sh` verifies `PINS.sha256`, then builds 8 binaries:
  `gcc|clang` x `vulnerable|fixed` x `asan|plain`, from `harness/driver.c`.

The driver uses **real** `cjose_jwk_import`, `cjose_jwe_encrypt`,
`cjose_jwe_export`, `cjose_jwe_import`, `cjose_jwe_decrypt`, real
`cjose_base64url_encode` and real OpenSSL `AES_wrap_key`/`AES_unwrap_key`.
It includes the pinned internal header `src/include/jwe_int.h` only to print
`jwe->cek_len` and `jwe->to[0].enc_key.raw_len` and to compare the declared
32-byte CEK with the independently computed transform. No patched upstream
source is generated by the harness; all upstream bytes are pinned files.

## Scenarios

`valid`: untouched compact JWE, 40-byte RFC 3394 wrapped CEK.
`odd`: 41-byte encrypted_key segment — OpenSSL rejects non-multiple-of-8
input before its copy, a negative that bounds the reachable write.
`probe`: 48-byte all-`0x41` encrypted_key, invalid IV — OpenSSL copies then
cleanses the output; ASan still reports the 40-byte write into a 32-byte CEK.
`wrapped`: 48-byte RFC 3394 wrap (under the upstream test KEK) of a 40-byte
chosen plaintext `0x5a` x 32 + `MISHE-OOB`; unwrap succeeds and writes 40
chosen bytes into the 32-byte CEK.
`wrappedbig`: 1024-byte wrap of 1016 chosen bytes — 984 bytes past the CEK.
`undersized`: 32-byte encrypted_key, too short for any CEK — rejects.

## Evidence

`harness/check.sh`: 8 binaries x 6 scenarios + one gdb probe; **223 PASS /
0 FAIL** on three consecutive runs, trace
`455b84940f98bf273d7007f8a054c4ff7f1b37017fd6afa7207a1bdb338e9da7`.
Raw per-invocation output: `harness/evidence/<binary>.<scenario>.out`;
normalized trace `harness/evidence/trace.txt`; summary
`harness/evidence/summary.txt`; gdb transcript
`harness/evidence/gdb-chosen.out`.

- Rung 1: `valid` decrypts to the 15-byte upstream test plaintext in all 8
  binaries; every tampered token still imports with `IMPORT=1 ERRCODE=0`.
- Rung 2: vulnerable `wrapped` finishes unwrap with `CEK_LEN_AFTER=40` on a
  32-byte allocation; first 32 bytes match the independent transform
  (`CEK_CMP_LEN=32 MISMATCHES=0`). Fixed `wrapped` rejects with
  `DECRYPT=0 ERRCODE=1` and keeps `CEK_LEN_AFTER=32`.
- Rung 3: gcc and clang ASan both report `heap-buffer-overflow`,
  `WRITE of size 40` (`wrapped`) and `WRITE of size 1016` (`wrappedbig`),
  allocation from `_cjose_jwe_malloc` at pinned `jwe.c:193`, with the copy in
  OpenSSL's `memmove`. Fixed ASan runs are clean for every scenario.
- Rung 4: gdb on `gcc-vulnerable-plain wrapped`, breakpoint on the library's
  `AES_unwrap_key` call (second hit; first hit is the harness's independent
  transform), `inlen=48`, destination `jwe->cek`; after the call the heap is
  `5a x32` then `4d 49 53 48 45 2d 4f 4f` ("MISHE-OO") at `cek+32..39` —
  chosen bytes at chosen offsets past the declared object.
- Negative: plain `wrappedbig` vulnerable aborts in glibc
  `free(): invalid pointer` (rc 134); `odd` and `undersized` produce no ASan
  report; the invalid-IV `probe` cleanses its output, so its bytes are not a
  chosen-byte claim.


## W181 — loopback wire consumer (2026-11-23 20:22-20:30Z)

New lab-only files: `w1/{server.c,client.py,build.sh,run.sh}` and text logs in
`w1/evidence/`. Build: `cd lab/frontier/cjose2shell/w1 && ./build.sh && ./run.sh`.
The server binds an ephemeral port on 127.0.0.1 only, accepts one real HTTP
GET with `Authorization: Bearer <compact JWE>`, independently base64url-decodes
the second segment, then calls real `cjose_jwe_import()` and
`cjose_jwe_decrypt()` from the pinned libraries. The Python client builds
RFC 3394 wraps locally with the same lab KEK; no external target is contacted.
Binaries: `w1-plain-vuln`, `w1-trace-vuln` (adds a static malloc/calloc/realloc
caller ring linked with `--wrap`, non-PIE), `w1-asan-vuln`, `w1-plain-fixed`.

Measured, with `EK_RAW_LEN` read from the wire segment and `CEK_LEN_AFTER`
reported by the library (`w1/evidence/<binary>.<scenario>.log`):

| scenario | write bytes | vulnerable plain | vulnerable ASan | fixed plain |
| --- | --- | --- | --- | --- |
| `valid` | 32 | rc 0, `CEK_LEN_AFTER=32`, HMAC fail (`ERRCODE=4`: synthetic ciphertext/tag) | clean | rc 0, same HMAC fail |
| `wrapped` | 40 | rc 0, `CEK_LEN_AFTER=40` | `WRITE of size 40`, `jwe.c:595` | rc 0, `ERRCODE=1`, `CEK_LEN_AFTER=32` |
| `wrappedN48` | 48 | rc 134, `munmap_chunk(): invalid pointer` | ASan OOB write | rc 0, `ERRCODE=1` |
| `wrappedN56` | 56 | rc 0 (`CEK_LEN_AFTER=56`) or rc 139 SIGSEGV; W183 below explains the variation | ASan OOB write | rc 0, `ERRCODE=1` |
| `wrappedbig` | 1016 | rc 139 SIGSEGV | `WRITE of size 1016` | rc 0, `ERRCODE=1` |
| `probe` (invalid IV) | 40 | rc 0, output cleansed, no chosen bytes | ASan OOB write | rc 0, `ERRCODE=1` |

The 48-byte case aborting is deterministic (`munmap_chunk()`); the 56-byte
case varies. Author repeats and an independent witness clean-room replay
observed both rc 0 and rc 139 SIGSEGV across builds/runs (W182 repetition
log `w1/evidence/wrappedN56-variation-w182.log`: 2/12 plain and 1/12 trace
rc 139). The witness traced one rc 139 to `__strcmp_avx2` from
`_cjose_jwe_calc_auth_tag` (`jwe.c:1098`) via
`_cjose_jwe_decrypt_dat_aes_cbc` (`jwe.c:1400`) with `enc=0x0`.

W183 established the cause (`w1/evidence/wrappedN56-cause-w183.log`; the
author's gdb capture `w1/evidence/wrappedN56-gdb-w183.log` matches the witness
backtrace): the 25-byte jansson object at `cek+48` is a `json_string_t` and,
in different processes, is either the 13-byte `enc` value `A128CBC-HS256` or
the 6-byte `alg` value `A128KW`. The allocation ring, offsets, callers and
CEK address are identical in every run; only that object's semantic identity
swaps. In all 4 crashes of a 40-run instrumented batch,
`json_object_get(hdr,"enc")` returned the adjacent object; in all 36
survivors it did not. The 56-byte write overwrites that object's `type` field
at `cek+48` with the chosen byte `0x5a`, so `json_string_value()` returns
NULL and the real decrypt path calls `strcmp(NULL, ...)`; when the other
string occupies the slot, `enc` stays intact and decrypt returns `ERRCODE=4`.
Fixed-IV and ASLR-off batches still vary (7/60 and 6/60 rc 139), so neither
token randomness nor address randomization is the cause. Chosen bytes
`02 00 00 00 01 00 00 00` at that offset (valid JSON_STRING type, refcount 1)
removed the early strcmp fault in all 60 runs, including the 5 where `enc`
was the adjacent object; all 60 then aborted in `munmap_chunk()` because the
chunk size at `cek+40..47` stays corrupted. This is chosen-byte control of a
live jansson object's metadata in the real decrypt path, not pointer control:
the object's value pointer at +16 is past the 56-byte write. Pinning jansson's
per-process `hashtable_seed` with the public `json_object_seed()` setter
(`w1/evidence/wrappedN56-hashseed-w183.log`) makes the outcome deterministic
per seed: across 40 pinned seed values, seeds 19, 27 and 30 gave 6/6 rc 139
with the `enc` object adjacent, while the other 37 seeds gave rc 0 with it
elsewhere. Jansson auto-seeds from /dev/urandom at the first `json_object()`
(`deps/jansson-build/src/hashtable_seed.c`, `value.c:69-72`), so that random
seed is the switch selecting which same-size string occupies `cek+48`; the
crash fraction is the share of seeds in the first class, not a race, ASLR or
token randomness. No control-flow target; security grade unchanged. This is a
preserved contradiction, now causally explained, not an escalation.

Heap geometry in the plain vulnerable process (`w1-plain-vuln.wrapped.log`):
`CEK_MINUS16=...3100000000000000` gives a 48-byte glibc chunk (32-byte
request, 40 usable bytes). The dump from `cek+24` is
`5a5a5a5a5a5a5a5a 4d495348452d4f4f 3100000000000000 02000000...`:
chosen `MISHE-OO` at `cek+32..39` (the next chunk's `prev_size`, ignored
while that chunk is in use), intact next-chunk size `0x31` at `cek+40..47`,
then that chunk's user data at `cek+48`. The 40-byte write therefore corrupts
no header or object on this host; the first header corruption is the 48-byte
write, which matches the deterministic `munmap_chunk()` abort. This is the
host-specific consumer behavior the plant requires before exploitation work.

`w1-trace-vuln.wrapped.log` resolves allocations near the CEK: `off=+0`
32 bytes from `_cjose_jwe_malloc` (`jwe.c:193`, the CEK); `off=+48` 25 bytes
from `jsonp_malloc` (`deps/jansson-build/src/memory.c:28`, a jansson string);
`off=+96` 32 bytes from `jsonp_malloc` and 35 from `_decode`
(`src/base64.c:77`); `off=+144` 58 from `jsonp_malloc` and 65 from
`_cjose_strndup` (`src/util.c:119`); `off=+224` 48 from `_oct_new`
(`src/jwk.c:360`). The ring is 128 entries and may list one address twice
after realloc.

Real-consumer source inspection (provisioning only, not a deployed build;
corrected in W184):
`src/provisioning/mod_auth_openidc-2.4.15.1.tar.gz`, SHA-256
`b50b12beaf1c210e3f98d900306a0a7ea252aa1e2b77147cb3b2cb34072f3444`.
`src/mod_auth_openidc.c:3960-3967` dispatches a logout parameter before POST
authorization-response handling; `:2939-2942` with `:238` selects
`?logout=backchannel`; `:3154-3182` reads the attacker-posted `logout_token`
and calls `oidc_jwt_parse(..., oidc_util_merge_symmetric_key(r->pool,
cfg->private_keys, NULL), ...)` before any signature check. `src/jose.c:930-936`
calls `oidc_jwe_decrypt(..., FALSE)`; `:765-771` imports with
`cjose_jwe_import()` and calls `oidc_jwe_decrypt_impl`; `:703-747` calls
`cjose_jwe_decrypt()` over the supplied keys. None of these wrappers checks
encrypted_key length. The earlier claim that this path supplied "configured
symmetric keys" was wrong: `cfg->private_keys` is populated only by
`OIDCPrivateKeyFiles` with PEM RSA/EC keys (`config.c:879-905`), and cjose
rejects non-OCT JWKs for AES-KW (`src/vulnerable/src/jwe.c:574-579`), so an
AES-KW `logout_token` cannot reach the vulnerable unwrap through this key set.
The pre-signature id_token path does supply an OCT JWK: `proto.c:1426-1434`
creates it from `provider->client_secret` and calls `oidc_jwt_parse()` ->
`oidc_jwe_decrypt()` -> `cjose_jwe_decrypt()`, but `mod_auth_openidc.c:2116-2118`
requires a `state` cookie matched from an earlier authorization request.
Both remain source claims about an unbuilt consumer: they support the
advisory's pre-auth shape but do not replace a running deployment or witness
replay. In a real deployment the KEK is secret, so only the write length is
attacker-chosen; byte values are not.

## W184 — real mod_auth_openidc consumer (2026-11-23 22:10-22:18Z)

Built a real Apache module against the pinned vulnerable library and measured
the backchannel-logout POST from the source claim above. Everything is in
`w2/`; replay commands, hashes, raw request/response bytes, tokens, gdb log
and limitations are in `w2/README.md` and `w2/evidence/SHA256SUMS`.

- `w2/build.sh` copies the pinned trees, rebuilds cjose v0.6.2.4 with
  `-g -O0 -fPIC -fno-omit-frame-pointer` against the harness jansson 2.14
  prefix, writes local `jansson.pc`/`cjose.pc`, and builds mod_auth_openidc
  2.4.15.1 with `/usr/bin/apxs`. Static library SHA-256
  `6801ddac35126f61e0eb160c212597c66a1ce85c6e5743eac5f196c1b179581d`;
  module SHA-256 `f1be85cfaf9e2db3935bd5a775bd8e76406e64817a46be72e6517cd1fd6b24cd`.
  These are build-instance values for this checkout path: `-g` embeds the
  build directory, so the witness's replay in `/tmp` produced different
  module/library hashes without changing the measured result (DM #3079).
  Startup log: `mod_auth_openidc-2.4.15.1 - init - cjose 0.6.2.4, openssl-3.0.13`.
- Private Apache `127.0.0.1:18443` only, `Listen` bound to loopback,
  `OIDCPrivateKeyFiles` loading a generated RSA key under kid `w2-rsa-kid`.
  `probe.py` sends three raw POSTs to `/redirect_uri?logout=backchannel` with
  compact JWE encrypted_key raw lengths 56, 56 with kid, and 40 with kid;
  lab KEK `dfddb556b3b94eb2ef3d0f8d14b96085`. All returned HTTP 400; the
  instance was stopped and the port verified free.
- gdb breakpoints (module loaded as gdb's child, Yama ptrace_scope blocks
  attach) logged `W2_BACKCHANNEL_HIT`; `W2_OIDC_JWE_DECRYPT_IMPL_REACHED` in
  all three; `W2_CJOSE_JWE_DECRYPT_REACHED jwk_kty=1` and
  `W2_AES_KW_DECRYPT_REACHED raw_len=56/40 cek_len=0 jwk_kty=1` only with a
  matching kid; no `W2_AES_UNWRAP_KEY_REACHED` in any scenario.
  `CJOSE_JWK_KTY_RSA = 1` (cjose/include/cjose/jwk.h:32): the configured key
  is RSA, so cjose rejects it at `jwe.c:577` before the vulnerable copy.
- `apache_error.log` confirms the two kid cases failed with
  `invalid argument [file: jwe.c, function: _cjose_jwe_decrypt_ek_aes_kw,
  line: 577]` for both 56 and 40 bytes, and the no-kid case with
  `jose.c:753` "could not be decrypted with any of the 1 keys". The 40-byte
  control shows the rejection is key type, not length. No fixed-cjose build
  was needed: the precondition for reaching `AES_unwrap_key()` was never met.

Verdict: measured negative for AES-KW through the default backchannel
logout key configuration. The attacker-supplied oversized length reaches the
vulnerable helper, but no OCT KEK is configured on this path, so no overflow
occurred. Unauthenticated reachability of the corruption in a real deployment
stays UNKNOWN; the id_token path (proto.c:1426-1434) with an OCT JWK from
client_secret is an unmeasured source-level follow-up. The witness
independently replayed this lane from a clean archive and ESTABLISHED the
negative at the labeled real mod_auth_openidc / loopback scope (DM #3079).
No pointer/IP control, rung 5 or module patch.

## Ceiling (after W181)

Direct call plus a loopback-only HTTP consumer with a real compact JWE token
and a lab KEK. Attacker-controlled segment length is carried by a real HTTP
request into the real import/decrypt path; ASan and plain glibc corruption
are measured, including the exact object adjacent to the CEK. No deployed
consumer was exercised; a real loopback mod_auth_openidc build reached the
vulnerable helper but not the copy (W184). No credential, pointer/IP control,
shell command. The witness independently replayed the direct-call and wire
lanes from a clean archive (verdicts #3019/#3020) and the W184
real-consumer negative (DM #3079). The chosen bytes are the plaintext of a
lab-generated RFC 3394 wrap under a lab-known key; in a real deployment the
recipient KEK is secret, so only the write length is attacker-chosen. The
advisory's deployed pre-auth reachability and code-execution claim remain
UNKNOWN; rung 5 not attempted.
