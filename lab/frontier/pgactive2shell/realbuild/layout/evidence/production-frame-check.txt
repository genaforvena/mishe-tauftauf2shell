disassembly was of the instrumented opt build left by run-layout.sh, which
has a standalone pgactive_parse_replident_name symbol. Does the shipped,
non-instrumented build put live data in the overflowed words or consume

The spilled registers at +80..+104 are restored only by the `pop` sequence
on the success return. The error path reads `riname` from %r12 and never
touches those slots; errfinish unwinds to a setjmp buffer in an outer
frame, so the overwritten words are abandoned. No saved pointer, canary
or return address is consumed by the production build either.

glibc sscanf return-count probe (no PostgreSQL involved)
---------------------------------------------------------
Source: /tmp/pgactive-sscanf-probe.c (throwaway, outside the repo).
gcc 13.3.0, glibc 2.39, built with `gcc -O0 -fno-stack-protector` and an
oversized 256-byte `dst` so the long case cannot smash the probe's stack.
Format: "pgactive_%lu_%u_%u_%u_%s" as expanded from the pinned header;
dst filled with 0x7f before each call. Output (rc=0):

  input=empty-tail n=4 dst[0]=7f dst[1]=7f
  input=space-tail n=4 dst[0]=7f dst[1]=7f
  input=empty-tail n=5 dst[0]=78 dst[1]=00
  input=long       n=5 dst[0]=41 dst[1]=41

Four assignments (the only count accepted by the pinned `!= 4` check)
leave the `%s` destination untouched. Any non-empty `%s` match assigns a
fifth item, returns 5 and takes the elog(ERROR) branch. A success return
with an overflowing `%s` store is therefore not reachable on this host,
so the live `values[]`/`isnull[]` pointers are never corrupted on a path
that uses them.

Outcome
-------
The 06:15Z saved-pointer conclusion holds for the shipped, non-instrumented
library as well as the instrumented opt build. The only demonstrated
control remains the explicitly instrumented in-function marker (rung 4
AS LABELED). No IP, no command side effect, no rung 5. Author observation;
not an independent witness verdict.
