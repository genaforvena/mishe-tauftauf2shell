W23 results — can the image itself write a plausible top-chunk size? (2026-11-25 07:1xZ, author-side)

Question. W22 showed that a DEBUGGER-FORCED write of 0x21001 into the live top
chunk's size field (pad 16 MiB) lets dcraw_emu exit normally. W23 asks the
bounded next question from the wall: with the unmodified -O0 consumer, can the
crafted image alone put a valid size there? No debugger writes in this wake.

Probe. w23/sizefield.gdb breaks on the first OOB store (xtrans_demosaic.cpp:427,
idx >= 68644), disables it, breaks at :436 (free_omp_buffers), and prints the
8 bytes at (char*)main_arena.top + 8. MALLOC_TOP_PAD_=16777216. All inputs were
generated by the pinned, unmodified craft_uncompressed_poc.py from
w11/targetbeef.input. sysmem = 16,781,312 in every run.

Note on the printed words: the words shown are the four halfwords at the size
field, not a channel-aligned pixel; the exact mod-4 phase was not printed in
these runs, so do not infer a precise pixel/channel mapping from them.

Result: NEGATIVE within this knob family. Every reachable non-zero field has a
non-zero high 32 bits (>= 0x1_0000_0000, far above sysmem 16,781,312), so glibc
rejects it; the only way to make the high half zero in these runs was to zero
the whole field (size 0, also rejected). WhiteLevel only produced saturation
to 0xffff; uniform curve scaling and per-pixel zero bands (narrow and wide)
moved the low words but never removed the non-zero high word. The lowblue
variant was a harness typo (input path `uniflowblue.input`), NOT an observation.

Controls on three representative crafted inputs, pad 16 MiB:
  greenzero1 / unif0001 / zero-narrow:
    unmodified plain -n 1: rc 134, "corrupted size vs. prev_size" (first two)
    or "free(): invalid next size (normal)" (zero-narrow)
  fixed tree -n 1: rc 0, empty stderr; no-option plain: rc 0, empty stderr.
W21's debugger-forced 0x21001 remains the only demonstrated valid size.

Grade unchanged: rung 4 (file-chosen bytes at chosen offsets, including
allocator metadata read by free), NO chosen pointer/IP, marker, command, live
object, r5. This is a bounded negative, not a proof over all possible images:
a different CFA/dimension layout or a consumer that allocates inside
xtrans_interpolate() after line 177 could still change the phase. All runs
local, no wire, no debugger writes into the inferior.
