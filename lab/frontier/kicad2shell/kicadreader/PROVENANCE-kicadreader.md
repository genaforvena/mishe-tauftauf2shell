# kicad2shell — KiCad-own compound-file reader lane (2026-11-23 19:22Z wake)

## What is upstream, byte for byte

- `src/compoundfilereader.h` and `src/utf.h`: raw files from KiCad 10.0.6
  (`thirdparty/compoundfilereader/`), fetched read-only from GitLab at
  `https://gitlab.com/kicad/code/kicad/raw/10.0.6/...`. Hashes in
  `PINS-kicadreader.sha256`:
  `223e8b03fb1c6a2e2cd04f7c08836e08c690d6c96292e26e02ab601217e53014` and
  `d72da15116c186ad7dbf29c5ae9eaf55327b8c7985973021f11bf0b9dd873d20`.
  These are compiled verbatim; no edit, no `#line` marker inside them.
- `../realparser/pins/altium_binary_parser.h.class.slice`,
  `altium_binary_parser.cpp.ctors.slice`,
  `altium_binary_parser.cpp.readprops.slice` and both pinned
  `../pins/sch_io_altium.cpp.{vuln,fixed}.slice` are reused unchanged under the
  same `#line` file/line markers as the earlier lanes.
- `run.sh` re-verifies all three pin files (new reader 2/2, realparser 5/5,
  ParseLibHeader 4/4) before every build; evidence in
  `evidence/pins-verify.out`.

Fixture bytes are the four `.SchLib` containers generated by
`../realcfb/make_cfb.py` and independently read back by
`../realcfb/verify_cfb.py` (`olefile` 0.46, `ALL_FIXTURES_OK`). No new crafted
payload: the hostile key is still `SIZEZ=84215045` (`ind=0`), `SIZE-1=84215045`
(`ind=-1`) and the `SIZE+1`/`SIZE-1` ordering case.

## What is lab code

- `stubs.hpp` is the earlier lane's wx support layer (same `wxString`,
  `wxAtoi`, `ALTIUM_PROPS_UTILS`, scale helper), with the CFB shim replaced:
  there is no lab definition of `CFB::COMPOUND_FILE_ENTRY` here. The lab
  `ALTIUM_COMPOUND_FILE` wrapper owns the byte buffer, constructs KiCad's real
  `CFB::CompoundFileReader`, finds `FileHeader` via its `EnumFiles`/`IsStream`
  with a UTF-16 name comparison, and returns the real entry pointer. The
  verbatim upstream parser constructor calls the real reader's `ReadFile`.
- `driver_tail.cpp` reads the chosen stream through that reader, runs the
  verbatim `ReadProperties()` for the diagnostic key print, then calls the
  pinned `ParseLibHeader` with the same wrapper.
- `run.sh`/`check.sh` build g++/clang++ × vulnerable/fixed × asan/plain and
  run the same four scenarios as the earlier lane.

KiCad's own `ALTIUM_COMPOUND_FILE` class (`common/io/altium/altium_binary_parser.cpp`),
wxWidgets and `eeschema` are **not** compiled. The wrapper mirrors only the
reader calls the pinned slices reach; it is lab code, not upstream bytes.

## Observed result

`check.sh`: **38 PASS / 0 FAIL** on two identical runs, trace
`fffe73410576403f33943253a207db3e8493229babdfb8f30f4544aebcfd6260`.
Evidence in `evidence/`, one `.out`/`.rc` per compiler/build/scenario.

- `kicad-cfb: ... stream=107`, `real-reader: bytes=107 props=3 parse_error=0`,
  `real-key: SIZEZ=84215045` — KiCad's reader delivers the hostile key from
  the CFB `FileHeader` stream to the verbatim parser, no key whitelist.

  top frame `sch_io_altium.cpp.vuln:5919`, allocation from `resize` at
  `:5915`. Plain: `rc=0 size=1 first=72 GUARD7=11111111` then glibc
  `double free or corruption (out)` at process teardown.
- `attackneg`: ASan `SEGV` at `:5919`, plain `rc=139`. `attackfar`: ASan
  `WRITE of size 4`, `8 bytes before 4-byte region`; plain exits 0.
- Fixed: all eight build/scenario combinations exit 0 with
  `rc=0 size=1 first=72 GUARD7=11111111`, no ASan report.
- Baseline has no ASan report. All runs preserve the earlier lane's chosen
  offset and fixed control.

## Ceiling and negatives

The CFB container is still a minimal synthetic fixture, not a vendor-produced
`.SchLib`. wxWidgets, KiCad's own `ALTIUM_COMPOUND_FILE` class, a real KiCad
build or `eeschema`, an executed downstream `aFontSizes` consumer, a socket or
wire, pointer/IP control, a benign marker, a command and a witness verdict are
all absent. The chosen bytes land in ASan's left redzone (plain build: malloc
metadata), not an adjacent live object. Rung 5 stays UNKNOWN. The source-bound
downstream reads (`:2744`, `:2917`, `:5278`, `:5479`) remain guarded.

One build attempt failed before the first check: an edit to `run.sh` dropped
`#include "stubs.hpp"` from the generated driver, producing missing-type
errors. Restoring the include gave the two matching 38/38 traces above; the
failure is preserved here rather than erased.
