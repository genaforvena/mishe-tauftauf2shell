When an HNSW Index Lies About Its Capacity

Every saved HNSW vector index writes two numbers in its file header: how much space to allocate, and how many vectors to copy in. Neither hnswlib nor Spotify's Voyager checked that the second number fits inside the first.

Official Advisory & CVE Status (Updated November 9, 2026)

CVE: CVE-2026-124959 (VU#681158.1) · CERT/CC: VU#681158 (public KB note pending; coordinated in login-gated VINCE #4191) · Affected: nmslib/hnswlib (0.5.0–0.9.0) and Spotify Voyager (2.0.7–2.1.1).

Loading an untrusted saved vector index can corrupt the heap of the process serving a RAG pipeline. In nmslib/hnswlib and Spotify's Voyager loaders, the file controls both the allocation size and the number of records copied into it. A file that claims room for fewer vectors than it actually stores makes the loader write straight past that heap allocation, corrupting adjacent memory and crashing the worker.

This boundary matters when a service imports prebuilt .index, .hnsw, or .voy artifacts from an external bucket or user upload. The extension alone does not identify the parser: the affected path is an HNSW index opened by these loaders. Maintainers must validate count against capacity and check allocation arithmetic before reading records. Operators should restrict imported indexes to trusted sources until their deployed loader enforces those checks.

An HNSW index is a saved map for vector search. It contains vectors, graph links, and metadata for rebuilding the search structure without indexing the corpus again.

Two numbers in that header must agree:

  1. max_elements_: how many elements the destination buffer has room for (the capacity).
  2. cur_element_count: how many elements are actually stored in the file (the count).

For any well-formed index, the count cannot exceed the capacity:

cur_element_count <= max_elements_

Neither nmslib/hnswlib nor Spotify's Voyager checked that rule when loading an index from disk (CVE-2026-124959, CERT/CC VU#681158, public KB note pending). Both loaders allocate their level-0 heap buffer using the smaller max_elements_ capacity and then copy cur_element_count records into it. When a crafted file sets max_elements_ < cur_element_count, the deserialization path writes straight past the end of the heap buffer (CWE-787: Out-of-bounds Write).

Who is affected: A service that only loads HNSW indexes it generated itself on trusted storage does not expose this path. Operators should audit RAG services, multi-tenant vector stores, and CLI tools that open prebuilt .hnsw or .voy snapshots from external buckets, model hubs, or user uploads.

(Verified on the advisory baselines, nmslib/hnswlib v0.9.0 d9b3608 and spotify/voyager 2a2f1f1, as well as upstream HEAD as of 2026-11-05, hnswlib v0.10.0-rc.2 ca42672 and voyager 72de126.)

What the file header declares

An HNSW (Hierarchical Navigable Small World) index speeds up vector search by stacking sparse upper-layer shortcut links on top of a dense ground floor. That ground floor, called level 0, stores one fixed-size record per vector: its neighbor links, its float coordinates, and its integer label.

When saving an index to disk, saveIndex writes fixed-width binary header fields before streaming the level-0 buffer and per-element link lists. When reading it back, loadIndex pulls three numbers from that header:

  • max_elements_: the buffer capacity M
  • cur_element_count: the stored vector count C
  • size_data_per_element_: the byte stride S of each level-0 record

The rule C <= M is not just bookkeeping. It decides whether the heap buffer is big enough to hold the bytes about to be read from disk:

capacity M from file   (max_elements_)
count    C from file   (cur_element_count)
stride   S from file   (size_data_per_element_)

allocate:  M * S bytes
read:      C * S bytes into that allocation

memory-safe only when:  C <= M  (and M * S does not overflow size_t)

A crafted file can contain all C element records on disk and still overflow memory on load. Checking the file length only proves that the source stream has enough bytes to read; it does not prove that the destination heap buffer has enough room to hold them.

Where the loader trusts the wrong field

nmslib/hnswlib (hnswlib/hnswalg.h, d9b3608 and ca42672)

The Python binding asks the loader to size the buffer from the file header. The loader reads both the saved capacity and the saved element count, never checks that the count fits inside the capacity, allocates from max_elements, and copies cur_element_count records into that buffer:

readBinaryPOD(input, max_elements_);
readBinaryPOD(input, cur_element_count);

size_t max_elements = max_elements_i;
if (max_elements < cur_element_count)
    max_elements = max_elements_;
max_elements_ = max_elements;

// Allocates M * S bytes from max_elements:
data_level0_memory_ = (char *) malloc(max_elements * size_data_per_element_);

// Reads C * S bytes from cur_element_count into data_level0_memory_:
input.read(data_level0_memory_, cur_element_count * size_data_per_element_);

Right after that bulk read, loadIndex makes the same mistake twice more. It sizes linkLists_ (sizeof(void*) * max_elements) and element_levels_ (sizeof(int) * max_elements) from max_elements, then loops up to cur_element_count (for (size_t i = 0; i < cur_element_count; i++)), writing past both arrays while populating label_lookup_. The level-0 bulk read is simply the first overflow hit.

(Evidence note: Python binding passes max_elements_i = 0 by default at python_bindings/bindings.cpp:969 on d9b3608 and :971 on ca42672; C++ loader at hnswalg.h:728-733,776,779 on d9b3608, and loadIndexNoExceptions at hnswalg.h:862,865 on ca42672.)

spotify/voyager (cpp/src/hnswalg.h, 2a2f1f1 and 72de126)

Spotify's Voyager forked from hnswlib and inherited the same fallback in loadIndex (its load constructors in cpp/src/TypedIndex.h:153,169,185 and Python voyager.Index.load at python/src/bindings.cpp:1020,1100 always pass max_elements_i = 0).

Voyager carefully checks the file: byte offsets stay in range, enterpoint nodes fit the count, the element stride matches the configured space, upper-layer link lists reach the expected end of file, and each read returns the requested bytes (cpp/src/hnswalg.h:732,753,779,826,844). Those checks prove that the source file is complete. They do not prove that the destination allocation (M * S bytes at cpp/src/hnswalg.h:834) is large enough for the C * S bytes copied at :843.

Even more telling: both libraries already enforce C <= M inside resizeIndex, rejecting any request to shrink an in-memory index below cur_element_count. Only loadIndex left the check out. (Compare hnswlib/hnswalg.h:633-635 at d9b3608, resizeIndexNoExceptions at :671-673 at ca42672, and Voyager cpp/src/hnswalg.h:660-664.)

What the real loader tests showed

To test the real library loader, we built and saved a normal 512-point index (21 float dimensions and M_links = 4, giving a 128-byte record stride S = 128). We then changed a single header integer, max_elements_, from 512 to 2 (byte offset 8 in hnswlib, or offset 27 after the 19-byte metadata prefix in voyager), leaving all 65,536 payload bytes and link lists intact so every EOF check passes:

  • Controls (exit 0): Both the unmodified 512-point index (M = 512, C = 512) and a smaller legitimate index (M = 16, C = 8) load cleanly across every unpatched and patched build we tested.
  • Crafted (M = 2, C = 512, S = 128): Allocates 2 * 128 = 256 bytes and reads 512 * 128 = 65,536 bytes into that buffer. Release builds (-O2 -DNDEBUG) abort in glibc with malloc(): corrupted top size (exit 134). AddressSanitizer catches the 65,536-byte write into the 256-byte buffer (65,280 bytes past the end of the allocation) inside loadIndex:

Where an untrusted index enters a service

A process that only loads HNSW indexes it generated itself from local, integrity-protected storage does not expose loadIndex to untrusted input.

The vulnerability matters whenever a serialized HNSW index crosses a trust boundary:

  • Retrieval-augmented generation (RAG) pipelines or vector search services that import prebuilt .hnsw / .voy index artifacts from external buckets or model hubs.
  • Multi-tenant search services that load per-tenant or user-uploaded index snapshots.
  • Embedded desktop or CLI tools that open shared project workspaces containing precomputed vector indexes.

In those deployments, treating a serialized HNSW index as passive data grants its header authority over native heap allocation sizes and subsequent bulk writes.

Check the count against capacity before allocating

The fix belongs immediately after max_elements is resolved and before data_level0_memory_, linkLists_, or element_levels_ are allocated, paired with an overflow check on max_elements * size_data_per_element_:

if (cur_element_count > max_elements) reject_corrupt_index();
if (size_data_per_element_ != 0 && max_elements > SIZE_MAX / size_data_per_element_) {
    reject_size_overflow();
}

Without the second check, a header with a huge max_elements passes C <= M and wraps the multiplication to a tiny allocation instead. Both upstream variants need these two guards before any allocation. Expand the implementation notes below for the status-returning hnswlib diff and exception-throwing Voyager diff.

Implementation notes & C++ diffs for nmslib/hnswlib and Spotify Voyager

nmslib/hnswlib (hnswlib/hnswalg.h, v0.10.0-rc.2 loadIndexNoExceptions): Because v0.10.0-rc.2 supports HNSWLIB_ENABLE_EXCEPTIONS=OFF, loadIndexNoExceptions returns a Status object rather than throwing directly (<limits> is already included):

@@ hnswlib/hnswalg.h loadIndexNoExceptions
         size_t max_elements = max_elements_i;
         if (max_elements < cur_element_count)
             max_elements = max_elements_;
         max_elements_ = max_elements;
+
+        if (cur_element_count > max_elements) {
+            return Status("Index seems to be corrupted or unsupported: "
+                          "cur_element_count exceeds max_elements");
+        }
         readBinaryPOD(input, size_data_per_element_);
+        if (size_data_per_element_ != 0 &&
+            max_elements > std::numeric_limits<size_t>::max() / size_data_per_element_) {
+            return Status("Index seems to be corrupted or unsupported: "
+                          "level-0 allocation size overflow");
+        }
         readBinaryPOD(input, label_offset_);

(On v0.9.0 d9b3608, where loadIndex is void and uses exceptions, throwing std::runtime_error at the same point provides the equivalent guard.)

spotify/voyager (cpp/src/hnswalg.h at 72de126): Adds <limits> explicitly and throws std::domain_error:

+#include <limits>

We applied both diffs to upstream HEAD (ca42672 and 72de126) and loaded each file through the real library entry point under AddressSanitizer (Apple clang 21, arm64 macOS). Both controls still load (exit 0). The crafted M = 2, C = 512 file is rejected by the first check (exit 3, no ASan report). A header with max_elements = 2^60 and C = 512, which passes C <= M and overflows the unpatched loaders, is rejected by the second check.

Disclosure timeline

  • 2026-07-17: Reported hnswlib and voyager loadIndex capacity-vs-count heap out-of-bounds write to CERT/CC (tracked under multi-vendor case VU#681158), as neither repository enabled GitHub Private Vulnerability Reporting or published a SECURITY.md contact.
  • 2026-08-11 to 2026-09-07: Two other GitHub users independently raised the same missing capacity check in hnswlib in public: 3nesdeniz opened issue nmslib/hnswlib#673 (2026-08-11), and chakshu-dhannawat opened PR nmslib/hnswlib#677 (2026-09-07, open and unmerged as of 2026-11-05). The spotify/voyager half had no public issue or PR.
  • 2026-09-29 to 2026-10-13: CERT/CC conducted vendor outreach via VINCE and coordinated disclosure under VU#681158.
  • 2026-11-05: Public writeup published in coordination with CERT/CC for CVE assignment under VU#681158.
  • 2026-11-09: CERT/CC published CVE-2026-124959 (VU#681158.1 under CERT/CC VU#681158, public KB note pending; coordinated via login-gated VINCE Case #4191, affecting nmslib/hnswlib 0.5.0 through 0.9.0 and spotify/voyager 2.0.7 through 2.1.1).
