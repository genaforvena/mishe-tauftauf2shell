All traffic is 127.0.0.1; the plant starts both the RTSP server and the victim
pipeline. No credentials are requested or sent at any point (no DESCRIBE/SETUP
challenge, no Authorization header). The server serves one audio track with
  a=rtpmap:96 L16/44100/N
and sends short interleaved RTP packets after PLAY so rtspsrc propagates the
SDP-derived caps. Driver: bash lab/gst2shell-src/run_rtsp.sh

Key difference from the earlier SDP-parser harness: here the REAL rtspsrc
emits the application/x-rtp structure itself. No structure-name rename step is
needed. The caps field reaching the shipping depay is generated by the actual
RTSP client pipeline, not synthesized by the harness.

This is a different crash site from the direct set_caps harness
(gst_rtp_L16_depay_setcaps+480 -> srcpad->g_class). In the full pipeline the
same unbounded posn[i]=NONE writes corrupt a GLib GSource instead; the fault
surfaces later in the main loop. Both are cross-object corruption by the fixed
-3 pattern. Never chosen bytes.

Channel-count sweep through the same RTSP path (logs rtsp_sweep_*.log):

The fault site and whether segtrap spins are allocator/timing dependent; the
deterministic claim is "attacker-chosen channel count faults the victim", not
"this exact instruction always faults".

Honest boundary: this demonstrates a LOCAL, no-credentials, remote-protocol
caps-delivery path (attacker-controlled RTSP server -> victim rtspsrc client)
in the lab. It does NOT show any particular public service accepting attacker
SDP, and it does NOT give chosen-byte control, arbitrary pointer control, or
code execution. No external system was contacted.
