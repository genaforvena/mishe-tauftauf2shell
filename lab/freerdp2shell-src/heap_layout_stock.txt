--- analysis ---
Layout is byte-identical across all three sessions; only the ASLR arena base
changes. glibc geometry: requested 8820 -> usable 8824 -> chunk size 8832;
the next chunk's size field sits at out_buffer+8824 (4 bytes past the logical
8820-byte buffer), so the write immediately overwrites adjacent chunk metadata
— this is the source of the pre-existing 'double free or corruption (!prev)'.

Chunks fully inside the chosen-0xDE write (offsets 8820..16383):
  off  8816  sz 48    small structure
  off  8864  sz 144   structure with 0xffffffff / 1 fields
  off  9008  sz 48    C strings: "com\0freerdp\0chan..."
  off  9056  sz 64    TWO LIVE HEAP POINTERS
  off  9120  sz 48    zeros
  off  9168  sz 123024 large chunk / top

The 64-byte chunk at off 9056 holds pointers at user offsets 9072 and 9080:
  run 1: 0x00007fe870002ee0, 0x00007fe870002ee4
  run 2: 0x00007103a8002ee0, 0x00007103a8002ee4
  run 3: 0x000071bae8002ee0, 0x000071bae8002ee4
Each equals base + 0x2340 (= base + 9024) = user data of the string chunk at
off 9008. So a structure with pointers into a nearby string buffer sits
entirely within the overwritten range, and the chosen 0xDE bytes replace both
pointer values byte-for-byte.

Honest boundary: this moves 'pointer-bearing heap data is reachable by the
write' from UNKNOWN to OBSERVED and reproducible. It does NOT establish
grooming of a specific target object, a chosen pointer value, or a controlled
dereference of the clobbered pointers; the write is sequential and overwrote
whatever was adjacent in this unmodified allocation sequence. The pointers'
owning object was not identified (no allocation-site tracing, which would
perturb the layout). Post-auth default (/auth) and subsystem-supplied ADPCM
table remain lab conditions, as in the accepted wake-9/10/11 replay.
